## Confirmed findings (severity-ordered)

### [CRITICAL] schema-migrations — v4 DB without schema_version row is stamped v9, skipping all v5-v9 migrations (non-convergent, write-bricking)
- **File**: src/db/schema.ts:145-156
- **Problem**: initializeSchema only validates the v4 floor (ensureV4MemoryColumns) for an existing DB, then for the no-schema_version case stamps schema_version=CURRENT_SCHEMA_VERSION (9): `db.prepare('INSERT INTO schema_meta (key, value) VALUES (?, ?)').run('schema_version', String(CURRENT_SCHEMA_VERSION))`. It assumes a DB at the v4 floor is already at v9. Callers (server.ts:152-153, lib/direct-access.ts:20-21/32-33) then call runMigrations, which sees version 9 and runs nothing. I reproduced this with a true v4-only DB (all v4 columns, no v5-v9 objects, no schema_version row): after initializeSchema+runMigrations the DB is stamped version 9 but memory_links=false, core_memory=false, memories.valid_from=false, memories.stability=false, memories.agent_id=false. This is exactly the scenario the maintainers claim to support (comment line 149 'Stamp it from observed shape'; migrations.test.ts:87 'accepts a complete v4 DB with no schema_meta row'). The upgraded DB does NOT converge with a fresh DB, and the first write throws because insertMemory (repository.ts:11-26) inserts valid_from/valid_to/tx_expired/agent_id which do not exist — failing silently at open time and surfacing later as a confusing runtime error. This breaks the unit's core claim (v4->v9 zero data loss; fresh and upgraded DBs converge).
- **Fix**: When an existing DB passes the v4 floor but has no schema_version row, stamp schema_version=4 (the verified floor), NOT CURRENT_SCHEMA_VERSION, so the subsequent runMigrations applies v5-v9. Alternatively, run migrations from the v4 floor before stamping. Stamping the observed floor (4) is the safe, convergent choice.

### [IMPORTANT] api-wiring — Public unauthenticated /publish search has a write side-effect on non-published memories
- **File**: src/api/routes.ts:330-354
- **Problem**: registerPublishRoutes mounts /publish OUTSIDE the bearer prefix (serve.ts:273-276), so /publish/:namespace/search is fully unauthenticated. It calls handleSearch(db, embedder, { query, namespace, detail_level:'summary' }) (routes.ts:345-349). handleSearch unconditionally calls recordAccess() on EVERY result returned by hybridSearch (src/tools/search.ts:82-92), and recordAccess (src/db/repository.ts:451-468) does: `UPDATE memories SET access_count = access_count + 1, last_accessed_at = ..., importance_score = MIN(1.0, importance_score + 0.03), stability = stability + ... WHERE id = ?` plus an INSERT into memory_access_log. Crucially, recordAccess runs BEFORE the route's publishedIds post-filter (routes.ts:350-352), and the route deliberately does NOT pass access_level to handleSearch — so any anonymous caller can mutate access_count/importance_score/stability and inject access-log rows for ANY memory in the namespace, including memories that are NOT published (e.g. access_level 'confidential'). This is an unauthenticated write/state-pollution vector: it skews importance-based ranking and tier classification, and gives an attacker an unauthenticated write-amplification (1 search = N row UPDATEs + N log INSERTs) DoS lever, all on the public surface.
- **Fix**: Add a read-only/no-access-recording mode to handleSearch (e.g. an opt-in `record_access:false`) and pass it from the publish search route; or have the publish route filter to publishedIds BEFORE any access recording. The publish surface must be side-effect free.

### [IMPORTANT] p1-graph — normalizeName drops all non-[a-z0-9-] chars, can collide distinct entities to empty/identical keys
- **File**: src/graph/entity-store.ts:7-11
- **Problem**: normalizeName lowercases and strips everything except [a-z0-9-]. A name made entirely of symbols (e.g. '++', '#') normalizes to '' and would collide every such entity onto one row keyed by normalized_name='' (findOrCreateEntity matches on normalized_name, entity-store.ts:24-26). Distinct names like 'C++' vs 'C#' both normalize to 'c'. The regex extractor's vocabulary (PascalCase / known tools / file paths) makes this unlikely from extractEntitiesRegex, but the LLM-driven memory_extract_entities path can pass arbitrary names into findOrCreateEntity, where such collisions silently merge unrelated entities.
- **Fix**: Guard against empty normalized_name (skip or fall back to a hash of the original), and consider preserving more distinguishing characters or appending the entity type to the normalization key to reduce cross-type collisions.

### [IMPORTANT] p3-retrieval — Cross-encoder reranker returns constant 1.0 in production — rerank:true is a silent no-op
- **File**: src/search/reranker.ts:56-61
- **Problem**: rerank() runs the ms-marco model through the @huggingface/transformers 'text-classification' pipeline (initialize() at line 79) and reads `output[0].score`. The Xenova/ms-marco-MiniLM-L-6-v2 config has id2label={"0":"LABEL_0"} (a SINGLE label) and no problem_type set (confirmed via the model's config.json on HuggingFace). In TextClassificationPipeline._call (node_modules/@huggingface/transformers/src/pipelines.js:297-305), any model whose problem_type !== 'multi_label_classification' gets `softmax(batch.data)` applied. softmax over a 1-element vector is mathematically always [1.0] (verified in utils/maths.js:137 — exp(x-max)/sum = exp(0)/exp(0) = 1). So `output[0].score === 1.0` for EVERY (query,doc) pair. In hybrid.ts the reorder is `[...head].sort((a,b)=>sb-sa)` (line 310-314); with all scores equal to 1.0, sb-sa is 0 and V8's stable sort preserves the fused order. Result: the reranker can never reorder anything when the real model loads. The unit tests pass only because they inject StubReranker (reranker.test.ts:24-32), never the real CrossEncoderReranker (whose rerank body is under /* c8 ignore */). The doc comment 'the text-classification pipeline surfaces that logit as score' (line 54-55) is factually wrong — softmax destroys the single logit. Contrast graph/contradiction.ts:65 which uses the SAME pipeline correctly because its NLI model has 3 labels, so softmax is meaningful there.
- **Fix**: Don't use the text-classification pipeline for single-logit cross-encoders. Load the model + tokenizer directly (AutoModelForSequenceClassification) and read the raw logit `outputs.logits.data[0]` (optionally sigmoid for a 0..1 calibrated score) as the relevance score — this preserves the per-doc ordering signal. Alternatively run the model and bypass the pipeline's softmax. Add a non-hermetic/integration test (or at least assert that two clearly different-relevance docs get different scores) so the constant-score regression can't recur silently.

### [IMPORTANT] p4-writes — Bi-temporal invalidation commits outside the insert transaction — partial-failure retires the old fact with no replacement
- **File**: src/tools/store.ts:82-87, 142-145, 180-203
- **Problem**: In handleStore, both the NLI path (invalidateMemory at line 84, inside the for-loop) and the heuristic DELETE path (invalidateMemory at line 143) run as standalone auto-committed statements BEFORE the new memory is inserted in the persist() transaction (line 203). handleStore is called directly with no outer transaction (server.ts:174). If persist() throws — e.g. recordConflicts explicitly re-throws to roll back (store.ts:187), or insertMemory hits a constraint/disk error — the rollback only undoes the insert; the already-committed valid_to stamp on the old memory survives. Result: the contradicted/superseded fact is retired (gone from default search, which filters `valid_to IS NULL`, hybrid.ts:225) yet the replacement was never inserted. The vault silently loses the only valid copy of that fact from current queries. No test covers this cross-statement window.
- **Fix**: Move the NLI shortlist invalidation and the DELETE-target invalidateMemory call INSIDE the persist() db.transaction() (alongside insertMemory), so a failed insert rolls back the invalidation atomically — mirroring how recordConflicts is already wrapped. The NLI classify() calls (async, cannot be inside better-sqlite3's sync transaction) should run first to compute the contradicted id list, then the invalidate+insert happen together in the sync transaction.

### [IMPORTANT] p4-writes — NLI shortlist omits the parent_id filter the heuristic enforces — can invalidate a chunk child of a chunked document
- **File**: src/tools/store.ts:69-81
- **Problem**: The NLI candidate shortlist uses findNearDuplicates(db, embedding, 0.5, 5) (line 69) and then filters only on `valid_to === null` (line 78). It never excludes rows with parent_id != NULL. The heuristic path it is meant to complement explicitly skips chunk children: detectConflicts rejects `row.parent_id !== null` (conflict-resolver.ts:76). So when documents are ingested as chunks (ingest.ts stores children with a parent_id), an opt-in supersede store can match a single chunk child via vector proximity and invalidate just that one chunk via invalidateMemory (store.ts:84), leaving the parent document partially retired/corrupted while the heuristic would never have touched it. Inconsistent contradiction surface between the two detectors.
- **Fix**: Filter the shortlist to top-level rows only: add `parent_id IS NULL` to the SELECT at store.ts:73-77 (or skip hits whose row.parent_id is not null), matching detectConflicts' guard so NLI and the heuristic operate on the same candidate set (canonical memories, not chunk fragments).

### [IMPORTANT] p5-agentos — memory_reflect store can corrupt an existing memory when its insight is a near-duplicate (default path)
- **File**: src/tools/reflect.ts:150-178
- **Problem**: storeInsight takes `insightId = stored.memory.id` (line 157) without checking `stored.stored`. With the DEFAULT on_conflict='add', handleStore returns NOOP when conflict-resolver flags an exact/near duplicate (overlapScore > 0.85 in conflict-resolver.ts:85), and in that case it returns the EXISTING memory's id and row (store.ts:94-104 `{ stored:false, memory: rowToMemory(existingRow) }`). reflect then (a) runs `UPDATE memories SET provenance='reflection' WHERE id = insightId` (line 160) overwriting that pre-existing — possibly manual — memory's provenance, and (b) creates derived_from edges FROM that existing memory to each source_id (lines 169-176), mutating an unrelated memory's graph. If a source_id equals the deduped memory's id this even creates a derived_from self-loop. This is silent record corruption on the default path under realistic input (agent reflecting on a corpus and synthesizing an insight close to an existing one). It is masked in tests only because MockEmbeddingProvider vectors are near-orthogonal and the test inputs are distinct content (reflect.test.ts:103-133).
- **Fix**: After handleStore, bail out (or ADD anew) when `stored.stored === false`: e.g. `if (!stored.stored) return { error: 'insight duplicates existing memory ' + stored.memory.id };` OR force a fresh insert for reflection insights (pass a marker so the dedup NOOP is bypassed). Also skip any source_id equal to insightId to avoid self-loops.

### [IMPORTANT] p5-agentos — memory_communities hard-crashes (too many SQL variables) past ~32,766 entities
- **File**: src/graph/communities.ts:269-287
- **Problem**: summarizeCommunities builds `entityIds = [...communities.keys()]` (every entity in the graph) and interpolates one `?` per id into `WHERE id IN (${placeholders})` (line 270/275) and `WHERE entity_id IN (${placeholders})` (line 285). SQLite (better-sqlite3 build here: MAX_VARIABLE_NUMBER=32766) throws 'too many SQL variables' once the entity count exceeds that. Reproduced empirically: 33,000 entities -> summarizeCommunities throws 'too many SQL variables', so the memory_communities tool crashes. The entities table grows automatically via entity extraction with no upstream cap; the module docstring scopes to 'few-thousand-node graphs' (communities.ts:14-18) but nothing enforces or degrades at the boundary — it is a hard failure of the whole tool. (Same unbounded-IN pattern exists in pagerank.ts/graph.ts, so this is a codebase-wide habit, not unique to this file.)
- **Fix**: Chunk the IN-clauses (batch entityIds in groups of e.g. 900 and merge results), or join against a temp table / build the maps from a single full-table scan keyed on the just-computed community map instead of an IN over all ids. At minimum cap/guard and return a graceful error when entity count exceeds the safe limit.

### [IMPORTANT] p7-team-bruno — Union merge resurrects deleted memories — deletion is not representable, no tombstone, no merge base
- **File**: src/graph/graph-export.ts:73-152, 173-211
- **Problem**: exportGraph filters out invalidated rows (valid_to/tx_expired NOT NULL) at lines 79-81, and ExportedMemory (lines 18-30) has NO valid_to/tombstone field — a deleted memory is represented purely as ABSENCE from the artifact. mergeGraphs is a 2-way union by id (lines 179-185): a memory present in one artifact and absent in the other is always contributed by the present side. The git driver is wired `merge-graphs %A %B %A` (share.ts:83) — it receives only ours (%A) and theirs (%B), NEVER the merge base %O, so it cannot tell 'B deleted m1' apart from 'B never had m1'. Net effect: dev A deletes/forgets memory m1 and commits; dev B (whose clone still has m1) merges — m1 is silently resurrected. I verified this against the actual mergeGraphs: art([m1,m2]) ∪ art([m2]) yields ['m1','m2']. This is the exact 'deletion vs edit' case the review flagged, and it breaks the 'no data loss' framing in the opposite direction (un-deletion / GDPR-forget reversal in a team workflow).
- **Fix**: Make deletion representable and merge-aware. Either (a) emit invalidated memories as tombstone records (include valid_to in ExportedMemory and export rows with valid_to set), and in mergeGraphs treat a tombstoned id as winning over a live copy when its valid_to is newer; or (b) change the driver to a true 3-way merge that consumes %O (base) so absence-relative-to-base is interpretable as deletion. Document the chosen deletion semantics next to mergeGraphs.

### [IMPORTANT] p8-trust — Hard-forget leaves child-chunk content in FTS5 + vec indexes (right-to-erasure breach)
- **File**: src/tools/forget.ts:47
- **Problem**: handleForget(hard) calls deleteMemory(db, id), which only manually cleans memories_fts/memories_vec for the SINGLE target rowid and then relies on `parent_id REFERENCES memories(id) ON DELETE CASCADE` to remove child chunks. FTS5 (external-content) and vec0 virtual tables do NOT participate in FK cascades, so child chunks' index rows are orphaned. Empirically verified: store a parent + one child chunk containing secret 'swordfish', then handleForget({id: parent, hard:true}) -> memories=0, but `SELECT COUNT(*) FROM memories_fts WHERE memories_fts MATCH 'swordfish'` = 1 and memories_vec rows = 1. ingest.ts (src/tools/ingest.ts:110,130) creates exactly this parent+child structure on the primary ingestion path, so this is the common case. The erased content remains searchable via FTS and retrievable via vector search, and the orphaned external-content FTS rows point at a deleted rowid (index-integrity hazard). This directly breaks the GDPR 'hard erase ... no residue' claim.
- **Fix**: Before DELETE FROM memories, enumerate the full subtree (the target id plus all descendants via `WITH RECURSIVE` on parent_id) and run the FTS5 'delete' command + DELETE FROM memories_vec for EACH descendant rowid, not just the target. Apply the same fix to deleteMemoriesByFilter (same structural gap). Add a regression test that hard-forgets a parent with chunks and asserts memories_fts/memories_vec are fully clean.

### [IMPORTANT] schema-migrations — Error message and test reference a `migrate` CLI command that does not exist
- **File**: src/db/schema.ts:107-117

### [IMPORTANT] security — Rate limiter is bypassable via X-Forwarded-For in remote/proxied mode
- **File**: src/api/rate-limit.ts:110 (with src/cli/serve.ts:163-165)
- **Problem**: rateLimitMw keys each token bucket on `req.ip` (rate-limit.ts:110). In the remote deployment mode the app enables `app.set('trust proxy', 1)` (serve.ts:163-165), which makes Express derive req.ip from the client-supplied X-Forwarded-For header. I verified this empirically against the project's own express: a request with `X-Forwarded-For: 1.2.3.4` yields `req.ip == '1.2.3.4'` and `9.9.9.9` yields `9.9.9.9`. An attacker can therefore rotate the XFF value on every request to get a fresh full bucket, defeating the per-IP limiter precisely in the mode (non-loopback) where it is meant to protect the server. Rate limiting is effectively a no-op against a determined remote attacker.
- **Fix**: Do not key the limiter on the user-influenceable req.ip when behind a proxy. Either key on the immediate socket peer (req.socket.remoteAddress) plus a trusted, proxy-set identity header (e.g. CF-Connecting-IP validated against Cloudflare ranges), or set `trust proxy` to the specific proxy IP/CIDR rather than the hop-count `1` so a spoofed leftmost XFF entry is not trusted. Document that operators MUST front this with a real WAF/limiter, but harden the built-in one regardless.

### [IMPORTANT] security — Public unauthenticated /publish surface has no rate limit and runs embedding+rerank per search request (DoS)
- **File**: src/cli/serve.ts:252-254, 273-276; src/api/routes.ts:330-354
- **Problem**: The rate-limit middleware is mounted ONLY on /api and /mcp (serve.ts:252-254). The /publish/* routes are registered OUTSIDE those prefixes (serve.ts:273-276) and are intentionally unauthenticated. GET /publish/:namespace/search calls `await handleSearch(db, await getEmbedder(), ...)` (routes.ts:345), which runs hybridSearch -> query embedding + (optionally) the cross-encoder reranker — a CPU-heavy local model invocation — on every request, with no auth and no rate limit. An unauthenticated client can issue a flood of distinct search queries (each forcing a fresh embedding/rerank) and exhaust CPU, denying service to the MCP/API paths sharing the process. The index/page/graph routes also hit the DB unmetered, but search is the expensive one.
- **Fix**: Apply the rate limiter (a dedicated, possibly stricter bucket) to /publish as well, e.g. `app.use('/publish', limitMw)` before registerPublishRoutes. Additionally bound the public search cost: cap query length, debounce/cache by (namespace,q), and consider gating the embedding-backed search behind a smaller per-namespace budget separate from /api.

### [MINOR] api-wiring — as_of accepts any string with no ISO-8601 validation; malformed value gives silently-wrong point-in-time results
- **File**: src/schemas/index.ts:185-191, 343-349
- **Problem**: MemorySearchSchema.as_of and MemoryListSchema.as_of are `z.string().optional()` with no format check. Downstream (src/search/hybrid.ts:219-223 and src/db/repository.ts:343-347) the value is bound directly into SQL string comparisons `valid_from <= ?`, `valid_to > ?`, `tx_expired > ?`. SQLite compares these LEXICOGRAPHICALLY against stored zero-padded ISO timestamps. A caller passing a non-padded or natural-language value (e.g. '2026-1-1', 'yesterday', '2026') does not error — it returns a silently-wrong temporal slice (e.g. '2026-1-1' > '2026-01-31T...' lexicographically). MCP-only (no REST exposure), and stored timestamps are controlled, so impact is bounded, but a malformed agent-supplied as_of degrades to wrong-but-not-flagged output.
