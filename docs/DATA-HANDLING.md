# Data Handling

This page is a reference for operators. It covers what the MCP Memory Graph stores, how long it keeps data, and how data subject requests are served.

## Scope

Single-tenant. Maintainer plus internal team. Not designed for external customers or regulated workloads.

## What's stored

- `memories` table fields: `id`, `content`, `scope`, `namespace`, `embedding`, `access_level`, `expires_at`, `created_at`, `updated_at`
- Embeddings: 384-dimensional float32, generated by the local embedder (no third-party API calls)
- `memory_access_log` audit table; see `src/db/migrations.ts:47-58`

## Retention

No hard TTL by default. The `memory_consolidate` tool prunes old, low-access entries on demand. Per-memory `expires_at` is operator-set.

## Deletion

- `memory_delete` removes a record
- `memory_export` provides portability before deletion (used to satisfy data subject access requests)

## Encryption at rest

Not built in. Use FileVault on macOS, LUKS on Linux, or volume-level encryption (e.g. encrypted EBS) on cloud hosts.

## Encryption in transit

TLS terminates at the reverse proxy (Caddy / NGINX / Cloudflare Tunnel). The server itself speaks plain HTTP and binds to loopback by default. See `src/cli/serve.ts:159` for the loopback-vs-remote detection.

## Audit log

Every read is recorded in `memory_access_log`. Retention is operator-controlled: prune via SQL on a schedule if required.

## GDPR notes (internal-team use)

- Lawful basis: legitimate interest for internal tooling
- Data subject access request: `memory_export`
- Right to erasure: `memory_delete`
- The `access_level` field exists but is operator-set; no automatic classification is performed
